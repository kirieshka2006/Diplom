# Refactor Roadmap And 3NF Plan

## 1. Исходная точка

Проект сейчас представляет собой Django-монолит с одним приложением `meeting_reservation_system`.

Основные проблемы:
- почти вся прикладная логика сосредоточена в одном файле `meeting_reservation_system/views.py`;
- маршрутизация централизована в `bron/urls.py` без domain-level `urls.py`;
- шаблоны крупные, без общей `base.html`, со встроенными `style` и `script`;
- почтовая логика, отчёты, техподдержка, бронирования, управление комнатами и резервные копии живут в одном слое представлений;
- миграции в репозитории неполные: в коде и `__pycache__` есть следы изменений после `0001_initial`, но исходников миграций нет;
- runtime настроен на MySQL, но в репозитории лежит `db.sqlite3`, который отражает только базовую миграцию и почти не содержит данных;
- часть зависимостей и файлов не встроена в рабочую архитектуру: `djangorestframework`, `package.json` с Next.js-стеком, неиспользуемые шаблоны и спорные импорты.

## 2. Целевая архитектура

Нормальная модульная структура для этого проекта должна строиться не вокруг технических слоёв, а вокруг доменов.

Целевое разбиение:

```text
bron/
  settings/
    base.py
    dev.py
    prod.py
  urls.py

apps/
  accounts/
    models.py
    views.py
    urls.py
    services/
    selectors/
    forms.py
    templates/accounts/
  rooms/
    models.py
    views.py
    urls.py
    services/
    selectors/
    templates/rooms/
  bookings/
    models.py
    views.py
    urls.py
    services/
    selectors/
    templates/bookings/
  offices/
    models.py
    views.py
    urls.py
    services/
    templates/offices/
  reviews/
    models.py
    views.py
    urls.py
    services/
    moderation.py
    templates/reviews/
  support/
    models.py
    views.py
    urls.py
    services/
    templates/support/
  reports/
    views.py
    urls.py
    services/
    exporters/
    templates/reports/
  backups/
    views.py
    urls.py
    services/
    templates/backups/

common/
  permissions.py
  validators.py
  exceptions.py
  utils/
```

Практически это достигается в два прыжка:
- сначала модульность внутри одного существующего приложения, без ломки `AUTH_USER_MODEL` и URL;
- потом выделение доменов в отдельные Django apps.

## 3. Поэтапный план: от минимально болезненного к нормальной структуре

### Этап 0. Зафиксировать текущее состояние

Цель:
- убрать риск поломать рабочую систему до начала рефакторинга.

Что сделать:
- зафиксировать текущую схему БД как baseline;
- выгрузить схему production/MySQL отдельно от `db.sqlite3`;
- собрать список всех существующих URL и шаблонов;
- добавить smoke-тесты на ключевые маршруты: логин, регистрация, список комнат, карточка комнаты, создание брони, кабинет, техподдержка;
- вынести секреты из `settings.py` в переменные окружения;
- завести один журнал изменений и решений.

Почему это минимально болезненно:
- поведение системы почти не меняется;
- это чистый подготовительный этап, который уменьшает риск последующих миграций.

Критерий выхода:
- есть список критичных сценариев, которые можно быстро прогнать после каждой правки.

### Этап 1. Модульность внутри текущего приложения, без изменения внешнего контракта

Цель:
- разрезать монолитный `views.py`, не ломая URL, шаблоны и импортную структуру.

Что сделать:
- превратить `meeting_reservation_system/views.py` в фасад совместимости;
- создать пакеты:
  - `meeting_reservation_system/views/accounts.py`
  - `meeting_reservation_system/views/bookings.py`
  - `meeting_reservation_system/views/rooms.py`
  - `meeting_reservation_system/views/offices.py`
  - `meeting_reservation_system/views/support.py`
  - `meeting_reservation_system/views/reports.py`
  - `meeting_reservation_system/views/backups.py`
- вынести `views_reviews.py` в `meeting_reservation_system/views/reviews.py`;
- оставить старые импорты в `bron/urls.py`, но внутри `views.py` только переэкспортировать функции из новых модулей;
- вынести общие проверки ролей в декораторы или хелперы, а не копировать `if request.user.role ...` по всем функциям;
- вынести в отдельные модули:
  - `services/` для прикладных действий;
  - `selectors/` или `queries/` для чтения данных;
  - `forms.py` для валидации HTML-форм;
  - `validators.py` для телефонов, кодов, profanity-check и т.п.

Почему это минимально болезненно:
- URL не меняются;
- шаблоны пока не трогаются;
- модели пока не трогаются;
- рефакторинг можно делать по одному домену.

Критерий выхода:
- `views.py` остаётся тонким фасадом;
- ни один доменный блок больше не зависит от кода соседнего домена напрямую.

### Этап 2. Разделить маршруты по доменам

Цель:
- убрать единую точку перегрузки `bron/urls.py`.

Что сделать:
- создать `urls.py` по доменам;
- в корневом `bron/urls.py` оставить только include:
  - `accounts/`
  - `rooms/`
  - `bookings/`
  - `support/`
  - `reviews/`
  - `reports/`
  - `offices/`
  - `backups/`
- переименовать маршруты так, чтобы названия отражали домен: например `bookings:create`, `support:ticket_detail`, `rooms:detail`;
- на этом же этапе удалить мёртвые пути и добить отсутствующие связки между `view` и `template`.

Почему это уже средняя боль:
- меняются namespace маршрутов;
- нужно аккуратно пройтись по шаблонам, `redirect`, `reverse`, `fetch`.

Критерий выхода:
- корневой роутер не знает бизнес-логики;
- каждая функциональная зона маршрутизируется отдельно.

### Этап 3. Привести шаблоны в нормальную структуру

Цель:
- убрать HTML-монолиты и встроенную frontend-логику из шаблонов.

Что сделать:
- ввести `base.html`;
- разложить шаблоны по доменным каталогам;
- вынести встроенные `style` в статические CSS-файлы;
- вынести встроенные `script` в статические JS-файлы;
- выделить partials:
  - navbar
  - alerts
  - booking cards
  - review blocks
  - modal forms
  - filter panels
- убрать дубли между `room_detail.html`, `all_reviews.html`, `support.html`, `admin_panel.html`, `manager_panel.html`.

Почему это средняя боль:
- меняются шаблоны и фронтовые связи;
- возможны регрессии в DOM и AJAX.

Критерий выхода:
- большие шаблоны разбиты на частичные блоки;
- inline JS/CSS сведён к минимуму.

### Этап 4. Вынести бизнес-логику из views в сервисный слой

Цель:
- чтобы view только принимал запрос, валидировал вход и возвращал ответ.

Что сделать:
- создать сервисы:
  - `booking_service`
  - `room_service`
  - `ticket_service`
  - `review_service`
  - `email_confirmation_service`
  - `backup_service`
  - `report_service`
- перенести туда:
  - проверку доступности комнаты;
  - создание бронирования;
  - обновление статуса брони;
  - отправку подтверждений;
  - модерацию отзывов;
  - логику тикетов;
  - генерацию JSON/PDF-отчётов;
  - создание резервных копий;
- сделать так, чтобы ORM-запросы чтения шли через selectors, а не были размазаны по всем views.

Почему это важно:
- именно этот этап превращает проект из набора handler-функций в поддерживаемое приложение.

Критерий выхода:
- view не содержит тяжёлых ветвлений, вычислений и склейки бизнес-правил.

### Этап 5. Нормализация БД до практической 3NF

Цель:
- убрать многозначные поля, дублирующие состояния и неявные сущности.

Этот этап нужно делать только после Этапа 1-4, потому что сейчас логика и шаблоны слишком тесно привязаны к текущим полям.

Подэтап 5.1. Убрать очевидные нарушения 1NF и подготовить 3NF

Сделать:
- убрать `Room.equipment` как текст со списком через переносы;
- убрать `Room.amenities` как JSON-список;
- нормализовать офисные удобства, если там реально список значений, а не одно описание;
- ввести отдельные справочники и связи many-to-many.

Минимальный целевой вариант:

```text
room
equipment
room_equipment
amenity
room_amenity
office_amenity
```

Почему это обязательно:
- текущие `equipment` и `amenities` не являются атомарными значениями;
- по ним невозможно нормально искать, фильтровать, валидировать и индексировать.

Подэтап 5.2. Убрать явную избыточность состояний

Сделать:
- удалить `Room.is_active` и оставить один источник истины: `Room.status`;
- проверить необходимость `SupportTicket.auto_close_date`;
- проверить необходимость хранения дублирующих вычисляемых полей в будущем.

Почему:
- `Room.status -> Room.is_active`, значит в модели уже есть риск рассинхронизации;
- одно бизнес-состояние должно храниться в одном поле.

Подэтап 5.3. Развести сущности контакта и комментариев в бронировании

Сделать:
- не использовать `manager_comment` для комментария клиента;
- ввести как минимум:
  - `customer_comment`
  - `manager_comment`
- если бронь может оформляться на отдельное контактное лицо, вынести контакт в отдельную таблицу `booking_contact`.

Минимальный целевой вариант:

```text
booking
booking_contact
```

где `booking_contact` хранит:
- `booking_id`
- `full_name`
- `email`
- `phone`

Если по бизнесу контакт всегда один на бронь, можно держать `OneToOne`.
Если в будущем контактов может быть несколько, делать `ForeignKey` на `booking`.

Подэтап 5.4. Нормализовать email-подтверждения

Сделать:
- определить один источник истины для верификации email;
- либо оставить `User.email` и `User.email_verified` как осознанную денормализацию;
- либо перейти на более строгую схему:

```text
user_email
  user_id
  email
  is_primary
  verified_at

email_confirmation
  user_email_id
  code
  created_at
  confirmed_at
```

Рекомендация:
- на первом проходе не трогать `AUTH_USER_MODEL`;
- email-нормализацию делать позже и только после стабилизации auth flow.

Подэтап 5.5. Проверить служебные сущности

Сделать:
- решить судьбу `DatabaseBackup`:
  - либо реально использовать модель как каталог резервных копий;
  - либо удалить её и оставить файловую реализацию;
- если нужен аудит, вводить отдельные таблицы истории:
  - `booking_status_history`
  - `ticket_status_history`

## 4. Что сейчас не соответствует 3NF или близко к этому

### Явные проблемы

`Room`:
- `equipment` хранит повторяющиеся значения внутри одного текстового поля;
- `amenities` хранит список в JSON;
- `status` и `is_active` дублируют одно и то же состояние.

`Office`:
- `amenities` почти наверняка список, но хранится одной строкой;
- `parking` и `transport` могут быть либо описанием, либо множественными атрибутами; если это список, их тоже надо нормализовать.

`Booking`:
- `manager_comment` используется не по смыслу;
- `booking_full_name`, `booking_email`, `booking_phone` являются отдельной сущностью контакта, если контакт живёт независимо от самой записи брони.

### Потенциальные, но не обязательные к немедленному исправлению

`User`:
- `email_verified` может рассматриваться как денормализованный флаг относительно подтверждений email;
- менять это сразу не нужно, потому что auth и регистрация сейчас и так хрупкие.

`SupportTicket`:
- `auto_close_date` может быть вычисляемым полем, если правило автозакрытия фиксировано и не требует ручного изменения.

`DatabaseBackup`:
- хранит метаданные, которые сейчас фактически дублируются файловой системой и не участвуют в рабочем потоке.

## 6. Порядок миграции БД без лишней боли

Правильная последовательность:

1. Добавить новые таблицы и новые nullable-поля.
2. Написать data migration для переноса данных из старых полей.
3. Переключить код чтения на новые таблицы.
4. Переключить код записи на новые таблицы.
5. Прогнать сверку данных.
6. Только после этого удалить старые поля.

Нельзя делать так:
- сначала удалять `equipment`, `amenities`, `is_active`, а потом пытаться собрать данные обратно;
- менять `AUTH_USER_MODEL`;
- одновременно ломать URL, шаблоны и схему БД в одном релизе.

## 7. Что делать в реальном порядке работ

Рекомендуемый порядок внедрения:

1. Этап 0: baseline, секреты, smoke-тесты, журнал.
2. Этап 1: разрезать `views.py` внутри текущего приложения.
3. Этап 2: разрезать `urls.py` и шаблоны по доменам.
4. Этап 3: вынести сервисы, формы, validators, permissions.
5. Этап 4: начать нормализацию `Room` и `Office`.
6. Этап 5: исправить `Booking` и комментарии.
7. Этап 6: решить судьбу email-архитектуры и backup-модели.
8. Этап 7: только после стабилизации выделять отдельные Django apps.

## 8. Текущее решение по базе данных

По состоянию репозитория:
- `bron/settings.py` настроен на MySQL;
- локальный `db.sqlite3` содержит только миграцию `0001_initial`;
- данных в `db.sqlite3` почти нет;
- значит реальной базой для проектирования нужно считать production/dev MySQL, а не этот SQLite-файл.

Следствие:
- прежде чем делать data migration под 3NF, нужно снять схему и объём данных именно с MySQL;
- `db.sqlite3` можно использовать только как локальный технический артефакт, но не как надёжный источник истины по данным.
